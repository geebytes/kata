# Replay repair returns during state recovery

Repair entrypoints — `/kata-build` after a verify FAIL, after blocking reviewer findings, or after a Judge FAIL — return the task to `implement` from `hardVerify`, `review`, or `judge`. Those backward events were appended directly, bypassing `transition()`, whose `isLegalPhaseTransition` accepts only the next phase in order. The append-only log therefore contained a chain link the recovery replay rejected. Because `status` rebuilds the mutable projection from the log whenever `requiresRecovery()` is true, the replay stopped at that repair link and rewrote `current-state.json` to the phase the task had been repaired from: the sealed `implement → hardVerify` progress never surfaced, and after a review-repair cycle the task could not advance past `review` at all, since every resume snapped the phase back there with the pre-repair timestamp.

`state.ts` now declares `repairReturnPhases` and exposes `isRepairReturn` plus `isReplayableTransition` (a normal forward step or a recognized repair return); `recovery.ts` replays chain links with `isReplayableTransition`; and `appendStateEvent` rejects any event that is neither the opening intake event, a forward step, nor a recognized repair return — so a future repair path cannot silently break the log again. `tests/unit/recovery.test.ts` covers `hardVerify`, `review`, and `judge` repair returns, asserting `requiresRecovery()` stays `false` and `recover()` keeps `hardVerify` instead of rewinding.

A task already rewound by an older build is repaired with `kata-cli recover --change <task-id>`, which rewrites `current-state.json` from the now fully replayable event chain.
