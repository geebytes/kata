# F3, F4 and F5: pricing a repair, deriving the check set, and stating a review's scope

The three remaining features of the finding-lifecycle design, in the order the document itself ranks them.

## F3 — a repair has a price (small)

`reverificationCostFor` is reported in every `adversarial brief` result: `passScope: 'delta' | 'full'` plus
`supersedesReceipt`, derived from whether the sealed revision records per-path digests (F2). It is the design's answer to
"fix one, grow two": the marginal cost of acting on a finding is now on the same account as the finding itself instead of
being invisible. A pass may also record `findingOrigins: { causedByPreviousRepair, note? }` (schema + type), so how many
defects a repair caused or left uncovered is a number in the record rather than an impression.

## F4 — the platform derives which checks a change touches

`src/quality/relevant-checks.ts`. The design rejects per-project tiering (one general problem becoming N project
configurations, and every new project walking into it), so the default is **derived** from what the platform already has:

1. map each changed path (F2's change surface) to the acceptance rows that declare it (`implementationPaths` /
   `testPaths`, directories covering what is under them);
2. take the checks those rows declare, resolved by the same resolver a seal uses;
3. **fall back to the full set** whenever the mapping cannot be made — no matrix, no row declaring the path, rows whose
   declarations resolve to nothing — with `fellBackToFull` and `fallbackReason` saying which it was.

The seal runs the derived set on a re-seal and names the excluded checks in `diagnostics.derivedChecks`; the freeze points
still require everything (`--frozen`, `fullChecks`), and a check excluded from a run keeps its declaration, its id and its
place in `--list-checks`. Fallback is a hard requirement, not an optimisation: a derivation that silently under-runs is
worse than no derivation.

## F5 — a review states what it read, and the statement is read conservatively

`src/quality/review-scope.ts`, `review.schema.json`'s `reviewedPaths`, and `review --reviewed-path <path>` (repeatable).
The design marks this lowest-confidence and asks its hard question first — *if a repair changes a file the review never
read, and the defect is there, who finds it?* Nothing does. So the mechanism does not let a repair bypass review:

- a review that recorded **no** scope is read as covering the whole revision, so any change invalidates it (today's
  behaviour, and the safe direction);
- a review that recorded paths is invalidated by any change **outside** them — which is the honest answer, because the
  defect would be in a file nobody read;
- when an approval states no scope, the matrix's suggestion (`suggestedReviewedPaths`) is **offered in the result**, never
  written behind the reviewer's back: the design rests on the reviewer's honesty and says the platform cannot verify it.

## What the design asked for that is still not done

The design's own §11 lists assumptions it could not verify, and building F3/F4/F5 does not verify them:

- **F2's saving was never measured.** The mechanism exists; "10–22 minutes becomes 2–3" is still a projection, and it is
  the assumption F4 now rests on.
- **F4's derivation accuracy was never measured** on a real project — the fallback rate decides whether it saves anything,
  and the design says so itself: fallback must be the normal case for the mechanism to be safe, which means it may also be
  the common case.
- **F4 × `tier`/`coveredBy` interaction** (which wins, and how both are shown) is settled here — derivation narrows first,
  then tiers defer, then coverage pointers redirect — but not measured.
- **`pathDigests` cost on directory owned paths** (record size) is unmeasured; the design estimated 10³ entries.
- **F5 remains unverifiable by construction**: `reviewedPaths` is the reviewer's word.
